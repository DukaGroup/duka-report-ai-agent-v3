# Duka Report Agent

A custom conversation/reporting workspace with a **Python backend**, **React frontend**, and **admin panel**.

Conversations and reports use either **ChatGPT through the official Codex CLI** or **Claude through the official Claude Agent SDK**, signed in with shared workspace subscriptions managed by Devs. Python talks to `codex app-server` over local stdio or the pinned Claude SDK's bundled CLI. There is no API-key configuration or API billing fallback. Each provider manages its own authentication and renewal; the corresponding subscription limits apply. Neither connection imports existing ChatGPT/Claude chats or memories.

## VPS deployment

[Deploy without Docker](docs/deploy-without-docker.md) — installation under `/var`, with separate service/Nginx configuration files and setup scripts.

[VPS troubleshooting](docs/deploy-troubleshooting.md) — potential fixes if installation or database access fails.

## Start

Follow the deployment guide above, then open your configured HTTPS address.

1. Create the first workspace administrator with your own password.
2. Open **Cilësimet → Modeli**. Connect ChatGPT, Claude, or both; each has its own connection card.
3. For ChatGPT, open the OpenAI sign-in link and enter the one-time device code. The app detects completion automatically.
4. For Claude, open **Lidh Claude**, sign in on the official Claude page with a subscription, then paste its single-use code into the app's login dialog. The official CLI completes the login; authorization codes and credentials are excluded from traffic logs and model context.
5. Choose **Përdor ChatGPT** or **Përdor Claude**, select an available model, and send a message. Both subscriptions can stay connected; the selected provider is saved for the workspace and applies to new chats/reports for all members. Existing messages and saved reports are retained when switching.

For ChatGPT, an eligible subscription with Codex access is required. Enable **device code login** in ChatGPT security settings if necessary; workspace admins may need to permit it. Claude requires an eligible Claude subscription with Claude Code access. [Anthropic's subscription guidance](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan) describes SDK and subscription usage. Enter account passwords only on the provider's sign-in page. Workspace login and provider connections are separate: Devs connect ChatGPT and/or Claude once, and every member uses those shared connections and subscription limits. Only Devs may sign in, disconnect, select the workspace provider or inspect subscription account/usage details. Existing original Devs credential directories are adopted in place and recorded in `workspace_subscriptions`; other saved credentials are retained. Independent chat/report processes keep the acting member ID and separate workspaces; sharing provider authentication never shares local conversations, reports or database/company grants. Disconnecting or reconnecting one provider clears that provider's native conversation bindings across the workspace; the other connection remains signed in. Every local chat retains a separate native session per provider and reuses it on reopening. On provider changes the local chat context is replayed so the new provider has the conversation's messages.

Claude uses SDK-discovered models, JSON-schema report outputs and the same authorized reporting/attachment tools, complete snapshots, export rules, workbook sandbox and validation as ChatGPT. Built-in shell, file, browser and agent tools are disabled. Its processes use a filtered environment, restricted mode, disabled hooks and only explicitly supplied reporting MCP tools; project/user settings are not loaded. Do not add `--bare`: it disables subscription OAuth. The official SDK and bundled CLI are pinned together; `CLAUDE_BINARY` optionally overrides the bundled executable for development. Claude usage percentages are not fabricated; the UI links to the provider's usage page.

## Chat controls and roles

Every sent user message offers pencil (**Ndrysho mesazhin**) and retry (**Ridërgo**) icons while its chat is idle. Resend works without edits; editing loads the original message and attachments into the composer. Retrying restarts from that message, replaces its old answer and every later turn, and creates fresh native provider context using only the preceding messages and attachments. The replaced branch is archived. Reports from the replaced branch remain downloadable in the Reports library, and calculations from that branch cannot be reused in the new conversation path. Other chats remain unchanged.

When a chat is open, ordinary typing outside other form controls or dialogs goes directly into its composer. The composer and uploads remain available during a response or report. Sending another message interrupts the previous work and starts the new request with the same chat history; unsent uploads stay outside model context. Stop remains available alongside Send. Stop cancels local chat/report work and signals the owned native process immediately, without waiting for a provider interrupt RPC. Independent report cleanup runs concurrently, and native shutdown never holds the shared worker-registry lock. Stops during discovery/thread startup persist the submission key so late retries cannot restart cancelled work; the frontend retains an unsent draft and applies the confirmed terminal state without waiting for extra report/subscription refreshes. Running chats can also be deleted: their active chat/report jobs are stopped first, and saved reports remain in the Reports library. Replacement, upload, stop and deletion are serialized per chat for both providers; replaying an accepted request key only reconnects its original response.

**Arsyetimi** in the composer, **Modeli**, and **Cilësimet** selects reasoning effort from the chosen model's native capability catalog. Automatic uses the provider default. The setting is saved with the next accepted message and inherited by conversation reports, including workbook repair attempts. Unsupported levels are rejected before starting a message. Recording and spoken-reply controls have been removed from the frontend; legacy transcription endpoints remain compatible.

Roles are **Devs**, **President**, and **Manager**. Devs manage connections, grants, roles, recovery and system settings. Managers see only Conversations and Reports. President sees those business pages plus a Members section in Settings for adding/removing business members; configuration stays Devs-only. President can select database/company access when creating a member but cannot change existing grants or create/remove Devs accounts. Only Devs can manage Devs accounts. President automatically has access to every registered database and company, including future additions. Managers use only their assigned databases and companies. Existing administrators migrate to Devs and members to Manager, preserving IDs, sessions, messages, reports, and grants. Devs can change another user's role; self-demotion and removing the last active Devs account are blocked.

## Settings and appearance

The sidebar has one **Cilësimet** entry. Appearance is available to every member; President also has **Anëtarët dhe qasja**. Devs additionally see Account, shared Model connections, Data sources, Overview, Traffic and Activity. Moving these controls does not change backend authorization. **Pamja** offers Light, Dark and System themes, saved per browser. System follows live device changes; themes synchronize across browser tabs and apply before the workspace renders. All main surfaces, forms, dialogs, dropdowns, tables and status colors use the selected palette.

The **Shto një anëtar** dialog ignores backdrop clicks and Escape. It closes with its X or after successful submission; validation and server failures retain the form.

## Member database and company access

**Cilësimet → Anëtarët dhe qasja → Shto anëtar** includes database and company checkboxes in the account-creation request. **Zgjidh qasjen** edits an existing Manager's assignments. Select a database for complete database access, or expand **Kompanitë** and select individual companies. New Managers start without database access. President and Devs show all databases/companies selected automatically; Devs and President can add/remove members; only Devs configure the system or change existing members' roles and grants. Member removal revokes sessions and stops that member's work, hides the member from the active directory, and retains their historical records and grants. Removed memberships cannot be reactivated through the ordinary account update endpoint.

Company identity discovery supports Business Central company table prefixes, SAP Business One company schemas, and SAP FI client/company-code pairs. SAP clients are separate choices, so granting a company in client 400 does not grant its copy in client 500. Large company lists are searchable. Unsupported identity catalogs allow explicit complete-database access; company restrictions are never guessed.

These grants are enforced before data is read, for chat, model-authored calculations and Excel reports through both providers. Restricted SAP row sets are applied to each base table before joins and aggregation. Company-restricted tables without a verified boundary, cross-database/company views, and legacy arbitrary reporting scripts are unavailable to scoped Managers; use base tables or an appropriately separated reporting source. Changing grants invalidates affected calculation captures and stops report publication if its access changed during generation. Previously authorized saved reports and chat history remain retained. Existing source grants are preserved until explicitly replaced with database/company selections.

## Reports

Use **Reports → Create report**, select a template, and supply manual JSON rows:

```json
[
  {"month": "September", "revenue": 12500, "orders": 84},
  {"month": "October", "revenue": 14900, "orders": 102}
]
```

The backend saves the exact data snapshot/provenance, computes basic decimal totals, generates a report through your subscription, validates structured output, and automatically creates a formatted **Excel (.xlsx)** workbook, with Markdown, JSON, and source CSV available as additional downloads. Review AI-generated interpretations against the underlying data.

Reports without data or with an unconfigured source are saved as **blocked**, with an explanation; no report inference is sent. No figures or sample rows are inserted automatically.

Admin controls include member creation/disable, service/runtime status, and audit events. **Data sources** defines source metadata, registered-query datasets, and per-member access grants. SQL Server connects through private per-source settings entered in the admin form (or legacy backend environment variables) and approved query scripts. The admin panel tests connections, displays sanitized errors, and enables datasets. The assistant can discover authorized database tables, inspect columns/relationships, filter/join/aggregate real data, and save reports directly from chat, without manual dataset definitions. The frontend is Albanian. Chat replies and newly generated report narratives always use Albanian, including informal greetings without diacritics. Both providers share this system-level policy; earlier replies, input language and provider handoffs do not change it.

See [architecture](docs/architecture.md), [schema](docs/schema.md), and [SQL Server setup and query scripts](docs/database-connectors.md).

Chat messages and report cards are merged by their creation timestamps. A report stays at its original position when it finishes, and follow-up messages appear below it. Deleting a conversation moves it to **Të fshira**, preserving messages, settings, provider bindings and report links for restoration. Permanently deleting a selected trashed conversation detaches its saved reports in the same transaction; report records, snapshots and downloadable Excel files remain available in **Raportet**.

The subscription bridge supplies instructions directly and sets `project_doc_max_bytes=0` both in its private configuration and on thread start/resume. This avoids trying to load `AGENTS.md` with a filesystem helper inside Docker. Older rollouts that fail with the specific blocked-namespace instruction-loading error recover into a new restricted thread with local chat history replayed. Other resume failures are still surfaced. No kernel or Docker permissions are expanded. See the [official configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference).

## Uploaded reports and Excel language

Use the paperclip button in the chat composer to attach **Excel (.xlsx), CSV, text-based PDF, Word (.docx), or UTF-8 text** files. Each file may be up to 12 MB; send up to five attachments with a message. Files appear on that message and remain available when reopening the chat. Ask the assistant to analyze them, compare their figures, or create an Excel report from them. For an Excel reference, select **Përdor formatin** on its card. Its fonts, table colors/styles, column widths/order, header positioning and line/column/bar chart types inform the new workbook. The assistant translates sheet names and headings into the chat's language. Complex merged layouts, embedded artwork and macros are not cloned; old reference figures are never substituted for new source results.

New Excel reports localize the overview, worksheets, table headers, calculation labels, chart titles/legends/axes, narrative and explanatory notes to Albanian. English and Albanian have built-in standard labels; other languages use the subscription model's complete translation map. Source identifiers, business names, values and Excel formula syntax stay intact. Incomplete presentation translations block generation rather than silently mixing English headings into the result. Original snapshots remain immutable. Excel presentation caches are versioned and older workbooks are refreshed from their saved snapshots on download, without rerunning database queries or calling the model.

The Python backend stores uploads under the private data volume and exposes `list_attachments`, `read_attachment`, `query_attachment` and `create_attachment_report`. Permissions are checked by user and conversation. Previews are paginated; structured aggregates process all imported rows. Complete snapshots, additional analyses and Excel artifacts remain downloadable after deleting a conversation. Uploaded content is untrusted evidence, not instructions. It is extracted in a subprocess with CPU/memory/time limits and without database credentials; Excel formulas, macros and embedded document scripts are never executed. Cached formula values are identified as such; missing caches remain missing. Scanned PDFs need OCR before uploading because this reader extracts text only.

Excel format references retain per-sheet grouped/merged headers, font/fill/border styles, column widths, numeric formats, subtotal row appearance and freeze/print settings. The model uses `reference_table` with explicitly authored current-period Albanian headers and a one-to-one mapping to complete captured results; compatible grouped references cannot silently flatten into ordinary tables. Reference figures and formulas are never copied into new results. Older uploads upgrade their presentation metadata in the isolated reader when selected or read, preserving their captured data. Incompatible table dimensions require an explained equivalent layout rather than invented or dropped fields.

ChatGPT and Claude share guidance to explain analytical scope, included/excluded records, actual calculation methods, evidence checks, findings, assumptions and limitations in clear Albanian. Reports receive the same guidance in their generation prompt; longer methodology follows the primary financial view. Successful code execution or matching formatting never certifies the model's business interpretation.

Limits: 20 worksheets, 10,000 rows per table, 100 columns, 200,000 worksheet cells, 100 PDF pages, 200,000 extracted text characters and a 25-second parsing timeout. Chat exploration uses 500-row/100-KB previews; Excel uses all imported matching rows independently of that preview limit. Upload storage is bounded to 250 MB per user and 50 files per conversation. Include `/data/uploads` in normal backups of the `workspace-data` volume.

## SQL Server setup

1. Start the application service and sign in as administrator.
2. Add a connection of type **SQL Server** using `SQLSERVER_HOST`, `SQLSERVER_PORT` (default 1433), `SQLSERVER_USER`, and `SQLSERVER_PASSWORD`. `SQLSERVER_DATABASE` is optional: leave automatic discovery enabled to discover every accessible online business database. Existing `.env` connections remain supported and private. Use a dedicated database login with SELECT permissions only.
3. Save, then click **Test connection**. Existing sources have **Configure connection** so you can save settings without recreating the source or datasets. The form shows configuration presence and `.env` mode rather than exposing credential values. Blank form fields never delete stored settings. New form-configured connections always use their own `.env` profiles, even when a global `.env` connection exists. Legacy `.env` connections retain their private environment profile; additional named profiles apply only to environment-backed connections. Explicitly switching an environment connection to form credentials makes its settings independent. Administration shows connection status and sanitized errors.
4. Administrators automatically have analysis access to connected SQL Server sources. Grant members source access using **Qasja te burimi**; this includes the online business databases and tables available to that source's SELECT-only login. No datasets or query files must be defined for automatic analysis.
5. In chat, ask **“Zbulo tabelat e databazës dhe më trego çfarë të dhënash kemi.”** Then ask, for example, **“Analizo shitjet e muajit të kaluar dhe krijo një raport në shqip.”** The assistant discovers your actual schema and uses backend scripts for reads, joins, filters and aggregates.
6. An Excel report card appears directly in the chat, with progress and **Shkarko Excel** when ready. The same workbook is available in **Raportet**. A request for a report automatically creates Excel; users do not need to specify a file format. The original data and query scope are captured by the backend.

The assistant can submit one primary query plus up to eight named analyses for period trends, comparable periods, breakdowns and supporting detail. Excel queries fetch every matching result row in batches from one cursor, with no TOP or offset pagination. The chat preview limit never limits the export. Full primary and additional datasets are retained in immutable snapshots and complete Excel tables; model context uses explicitly labeled bounded samples and model-authored summary datasets; the backend does not calculate numeric summaries. The model chooses financial metrics, comparison formulas, tables and charts in its calculation and workbook scripts. The backend does not infer financial measures from column names or impose accounting rules on new analyses. Unsupported or missing inputs must be identified rather than invented.

Result column aliases may be readable labels such as `Sales incl VAT` or `Posting Month`; the backend bracket-quotes them and rejects duplicates. Table aliases remain simple identifiers. Validation failures return field paths without private input values. Every supplied supplementary query must succeed in full, even when its legacy required flag is false. Connection/access failures, unavailable views and incomplete results stop generation instead of silently dropping analyses. Exceeding configured export capacity also fails clearly without publishing a partial workbook. Default REPORT_MAX_ROWS is 1,000,000 per result (within one Excel worksheet); REPORT_MAX_BYTES is 250,000,000 (250 MB) for the complete immutable report snapshot. Snapshot storage uses compact UTF-8 JSON without changing any data values. These capacities are distinct from chat previews and can be increased by the administrator. Reporting failure audit entries identify the stage and exception class without credentials or raw exception payloads.

Chat text and microphone controls remain locked while any of the user's reports are queued or running, including after the chat response ends and after reload. **Ndërprit raportin** explicitly cancels generation and unlocks input. The backend independently rejects chat messages during report generation. Excel files are written before a report becomes completed, retained privately under `/data/reports`, and downloaded only by their owner. Existing completed reports acquire an Excel export on first download without another model request. All dropdowns use accessible custom controls with keyboard navigation.

`list_sources`, `list_tables`, `describe_table`, `query_database`, and `create_database_report` are built-in Python tools; they never give the model credential files, SQL connection strings or shell access. Query plans are structured objects, not arbitrary SQL. They support up to four joined tables, scalar filters, date buckets (day/month/year), grouping, sorting and SUM/AVG/MIN/MAX/COUNT metrics. Chat reads return at most 500 rows and 100 KB and clearly mark previews; Excel export executes the same validated plan separately and reads every matching result row. Aggregation remains available for business summaries, without forcing the loss of full detail or breakdowns. Manual datasets/query files remain optional for curated or more specialized reports.

**Bisedat** opens a searchable conversation library with cards, message previews, counts and last activity. Clicking a card reopens that conversation; **Bisedë e re** opens a blank local draft. Sending a message, uploading a file or requesting a report creates the application's conversation record. Its first chat message starts a fresh Codex thread and saves that thread ID for subsequent messages. Opening a blank chat or reopening an existing chat does not start a Codex thread. Follow-up messages reuse the saved thread, including after worker recycling or restart. Background reports use separate report threads. Unassigned reports never appear in a fresh chat. **Raportet** provides cards with open, Excel download and delete actions. Reports open in a closeable preview with Excel, Markdown, JSON and CSV exports. Deleting a report moves it to **Të fshira**, where **Rikthe raportin** restores its data and downloads. Active reports must be interrupted before deletion. Both Reports and Trash have individual checkboxes, Select All, a selected count and deletion of the exact selected set. Active reports are excluded. Reports move to Trash; selected items in Trash are deleted permanently only after confirmation. A batch validates ownership, current view and eligibility for every selected ID before changing any reports or files; unselected reports and shared snapshots remain. All report operations check ownership; deleted reports and downloads return 404 until restored.

User messages appear on the right and assistant messages on the left. Delete conversations using the sidebar trash icon or **Historiku i bisedave** in the top bar (also available on mobile). Deletion moves conversations to their own **Të fshira** view. Restore brings back the same messages and context without restarting interrupted work. Trash has individual checkboxes, search-scoped Select All, single and bulk restore actions, and confirmed permanent deletion of selected chats. Bulk restoration validates the entire owned selection before changing anything and retains messages, settings and provider context without restarting work. Normal chat routes and completion notifications exclude trashed chats. Permanent deletion removes local messages and conversation evidence while retaining saved reports; provider rollout files and report snapshots are independent server records.

Chat turns send the original request without an extra report-style message. Responses and generated report prose stay in Albanian under a shared system-level policy. Background reports retain the original chat request as evidence of its scope; its language does not override that policy. The workspace base currency is Albanian lek (ALL), supplied as thread context and report metadata; blank/null/whitespace currency codes in recognized currency columns display as ALL in model report samples and Excel tables, including aliased Currency Code selections. A localized base-currency note identifies ALL in the overview and each worksheet. Explicit foreign currencies stay separate and are not converted without supported exchange-rate data. Amounts, unrelated blank cells, original snapshots and source query filters remain unchanged. Schema migration 8 refreshes old provider context once so removed injected style preferences are no longer carried forward, while local conversation history, attachments and reports are retained. Interface text uses larger relative font sizes, with visible captions at least 12 px and desktop chat text at 16 px at the default browser font size.

## Settings and persistence

Copy `.env.example` to `.env` only when overriding defaults. The project-root `.env` is mounted writable at `/run/duka.env` for the backend only. Before starting Docker on Linux, run `bash scripts/allow-env-write.sh` to grant container UID 10001 access while excluding other local users. Admin-saved SQL Server and SAP HANA connections each use a stable `DUKA_CONNECTION_<ID>_` prefix; unrelated settings are preserved. Legacy encrypted connection rows are migrated to this file on startup, and SQLite retains only a storage marker. Environment-backed connections retain their existing profile; generic environment values never override independently saved connections. Password characters such as `$` are preserved literally. Outside Docker, `Settings` reads the project-root file (or the path configured by `ENV_FILE`). Backend connection resolution refreshes changed settings; after replacing `.env` with an editor, rerun the permission script and `docker compose up -d --force-recreate` so editor file replacement and other container variables are refreshed. There is no API-key setting.

| Setting | Default | Purpose |
| --- | --- | --- |
| `PORT` | `8080` | Host port; also update `ALLOWED_ORIGINS` if changed |
| `ALLOWED_ORIGINS` | localhost/127.0.0.1 on 8080 | Exact allowed browser origins |
| `SECURE_COOKIES` | `false` | Use `true` behind HTTPS |
| `SESSION_HOURS` | `24` | App session lifetime |
| `VOICE_ENABLED` | `true` | Enable local transcription |
| `WHISPER_MODEL` | `base` | Local speech model |
| `WHISPER_LANGUAGE` | empty | Auto-detect, or ISO code such as `en`/`sq` |
| `MAX_CODEX_RUNTIMES` | `8` | Maximum live subscription-control runtimes |
| `TURN_TIMEOUT_SECONDS` | `0` | Model response wall-clock limit; `0` runs until completion or Stop |
| `DOCKER_DNS_PRIMARY` | `1.1.1.1` | Persistent upstream DNS; use LAN/VPN DNS for private database hostnames |
| `DOCKER_DNS_SECONDARY` | `1.0.0.1` | Second persistent upstream DNS resolver |
| `SQLSERVER_HOST` | empty | SQL Server hostname; backend only |
| `SQLSERVER_PORT` | `1433` | SQL Server TCP port |
| `SQLSERVER_USER` | empty | Dedicated SELECT-only login |
| `SQLSERVER_PASSWORD` | empty | Database password; backend only |
| `SQLSERVER_DATABASE` | empty | Optional default database; blank discovers accessible business databases |
| `SQLSERVER_ENCRYPTION` | `require` | Require encrypted database transport |
| `SQLSERVER_TIMEOUT_SECONDS` | `15` | Login and query timeout |

On the native VPS, SQLite, keys, uploads, reports, shared subscription credentials/native history and caches live under `/var/lib/duka-agent`. Configuration is read from the repository's `.env`. Back up this data directory and `.env` together, retaining the legacy credential key for older backups. `.env` is allowed in Git for this deployment and remains excluded from image builds, browser responses and model workers.

The app uses Docker's `unless-stopped` restart policy and explicit upstream DNS from the two `DOCKER_DNS_*` settings. This avoids inheriting an empty resolver list when Docker starts before the laptop's network is ready. On Linux, Docker itself must start at boot (`systemctl is-enabled docker`). Saved ChatGPT credentials are reused after startup. If the browser opens while the backend or account-routing service is temporarily unavailable, it checks again every five seconds and on network-online/page-visible events; requests do not overlap. Recovery stops once the connection service is available. This does not automatically initiate new logins or override expired credentials. If you deliberately stop the container, start it with `docker compose up -d`.

The container runs non-root with a read-only filesystem, dropped capabilities, a writable data volume, and a single writable project `.env` bind mount. The host port binds to loopback. Keep the prototype local; remote access needs an authenticated HTTPS deployment, secure cookies, exact origins, and appropriate subscription eligibility/deployment review.

## Troubleshooting

- **Device sign-in fails:** Enable device code login in ChatGPT security/workspace settings, check outbound OpenAI access, and start a fresh code.
- **Device-code request and workspace routing both fail after a restart:** DNS is now explicitly persisted in the container, and the frontend retries temporary connection failures automatically. Check `docker compose exec app python -c "import socket; print(socket.getaddrinfo('auth.openai.com', 443)); print(socket.getaddrinfo('chatgpt.com', 443))"`. If resolution fails after the network is online, ensure the two `DOCKER_DNS_*` settings point to resolvers reachable on your current LAN/VPN. Use your network's DNS when SQL Server has a private hostname. Changing these settings requires a one-time `docker compose up -d` after active work finishes; ordinary laptop/container restarts reuse them. Proxy/firewall restrictions and expired subscription credentials require their own fixes.
- **Usage limit reached:** Wait for the reset or manage your plan in ChatGPT. No API billing fallback is provided.
- **Model unavailable:** Reload the account/model picker and choose a permitted model. A catalog alone is not an entitlement guarantee.
- **Runtime capacity:** Administration → People & access → Restart an idle runtime, or increase `MAX_CODEX_RUNTIMES`. Saved credentials remain.
- **Microphone over a LAN IP:** Use HTTPS.
- **Voice fails:** Check model download access to Hugging Face and RAM/disk, or choose a smaller model.
- **Startup errors:** `docker compose logs --tail=100 app`. Access logs and Codex stderr are suppressed to avoid credential/auth-URL exposure.

## Sales-source discovery and admin traffic

For Business Central sales requests, `discover_sales` is a backend-only read script that discovers and probes posted invoice/credit-note base tables in the selected database. It ignores stale company-named views and extension tables without monetary fields. Discovery covers every usable company, including legacy tables without app GUID suffixes. A recommendation is local to one database; multiple companies do not force a choice. Explicit user scope is respected, and duplicate/archive records must be investigated before consolidation. It returns the current Europe/Tirane business date and posting-date, document-number join and ALL currency guidance. A successful empty-period database query can produce an Excel report identifying its scope without inventing transactions. SQL 208 on a view returns an actionable discovery hint; it does not mean the saved database credentials disappeared.

The existing `SQLSERVER_*` settings remain supported. An optional complete `GOTECH_SQLSERVER_HOST`, `GOTECH_SQLSERVER_PORT`, `GOTECH_SQLSERVER_USER`, `GOTECH_SQLSERVER_PASSWORD`, `GOTECH_SQLSERVER_DATABASE` profile in the mounted `.env` takes precedence for the source named **GoTech** only. Partial named profiles fail as incomplete instead of borrowing credentials from another connection. These values stay in Python and are not passed to Codex.

**Administrimi → Trafiku** shows the latest 10,000 persisted application events, refreshed every two seconds, with direction filters, older pages, pause/resume and event details. It observes HTTP request/response metadata (including the full SSE duration and response byte count), Codex stdio messages, tool calls and SQL operations. Correlation IDs, worker/process IDs, statuses, timings, result counts and SQL error codes help trace failures across concurrent chats. Health checks and traffic-viewer polling are excluded. The **Hap** action loads an event’s redacted request/response contents, model messages, tool arguments/results, SQL queries/parameters and results, or Excel script/validation details. Content is fetched separately from the event list and is admin-only. Previews are bounded to 64 KiB, 100 items per list and 20,000 characters per string, with explicit truncation flags. Authentication, connection configuration, cookies/tokens and binary bodies are excluded; known database credentials and private-key material are redacted. Existing events from before this upgrade contain metadata only. There is no direct frontend-model connection: the Python backend mediates it. This is application traffic, not raw TCP/TLS packet capture or inspection of the CLI’s encrypted provider connection. The log is admin-only, bounded, batched to avoid per-token SQLite writes, and retained in the private Docker data volume across restarts.

## Permanently empty report trash

In **Raportet → Të fshira**, **Zbraz koshin** opens a confirmation showing the current deleted-report count. Confirming removes only the signed-in user's soft-deleted reports, cached Excel files and leftover report temporary files. Their snapshots are removed only when no retained report references them. Current reports, other users' trash, conversations, uploads and original business database records remain available. Restore and purge are serialized in a database transaction; storage failures retain report records/snapshots for recovery. A bounded audit event records the purge count. This operation is permanent; the normal delete button still moves a report to recoverable trash.

The subscription model supplies narrative, translated headings and an analysis/presentation plan. The Python backend (`workbooks.py`) constructs the actual XLSX sheets, places table rows and columns, adds deterministic formulas and builds charts. Workbook row/column alignment is controlled by that export code and the supplied presentation metadata.

## Model-generated workbook Python

New report tasks request `workbook.python_script` from the connected subscription model. The script defines `build(report)` and chooses readable output sheets, narratives, source-bound metrics/comparisons, tables and charts using the documented report helpers. Source retrieval remains in authorized backend tools. Chat also has the restricted data-calculation tool described below; it has no general Python, shell or filesystem access.

Each workbook runs in its own cancellable Python subprocess, with up to four jobs concurrently. The worker receives only the report document and immutable source snapshot. It starts with a minimal environment, isolated Python imports and closed inherited descriptors. Trusted modules and input are loaded before untrusted execution; only two job-local output handles remain open. Linux x86_64 Landlock ABI 3+ and a seccomp syscall allowlist are required. After isolation, all file-opening syscalls, networking, process creation and execution are denied. AST validation additionally limits Python to local variables, loops/conditions and approved report helpers, preventing raw library access, imports, eval, private attributes and helper/source mutation. Unsupported isolation fails closed. No Docker socket, elevated container capabilities or weaker native Codex permissions are introduced.

Defaults are WORKBOOK_SCRIPT_TIMEOUT_SECONDS=300 and WORKBOOK_SCRIPT_MEMORY_MB=4096; valid ranges are 1–300 seconds and 256–4096 MB. CPU, address space, file size, descriptor and core-dump limits apply. Cancellation/timeout kills the worker and removes its private job directory.

The trusted writer always adds complete visible source tables independently of the generated output layout. Output sections advance vertically so text, tables and charts cannot occupy the same reserved rows. Currency-specific calculations use the original source rows, preserve ALL/foreign currency separation, and expose source-linked formulas where supported. Full raw detail is retained even when readable charts show at most 1,000 categories, with a scope note. Numeric values beyond Excel's precision remain exact text; dependent calculations stay unavailable. Source tables remain authoritative; model-authored narrative is still interpretation, not a verified financial assertion.

Before publishing, the backend independently reopens the Excel file and compares every source cell, row count, table boundary, heading and currency against the snapshot. It also reconciles generated helper calculations and output tables, and rejects external connections, macros and unsupported formulas. Script execution/validation errors return to the same report-model thread for at most two repairs (three attempts total). A failed report publishes no downloadable partial workbook. Audit metadata includes attempt count, script SHA-256 and verified row/calculation counts without business values.

Scripts are saved with the owner-protected report document, allowing validated regeneration without a new model request. Existing reports without a script retain the historic deterministic exporter. The model chooses a new custom layout by default; `default_layout()` remains available for explicitly requested legacy layouts.

## Duka Group branding and discovery across databases

The frontend uses the official Duka Group navy/blue palette and locally stored official logos in the sidebar, sign-in screen and browser icons. Asset provenance is in `frontend/public/brand/README.md`. No runtime request to the corporate website is needed.

The assistant begins database work with `discover_databases`, which inventories every granted SQL source and paginates every accessible online business database. System databases are excluded. Catalog discovery uses master so an unavailable default business database does not prevent discovery elsewhere, with a configured-database fallback for restricted logins. Tables, descriptions, sales discovery, previews and Excel reports accept an explicit `database`. Selection is checked against the server catalog and actual login permissions; it cannot supply SQL or connection credentials. Each request uses its own connector, so simultaneous chats cannot switch one another's database. A failed source is reported explicitly while other source catalogs still return.

`create_database_report` supports primary `source_id`/`database` and a separate `source_id`/`database` in each of up to eight supplementary analyses. Omitted source inherits the primary source; omitted database inherits the primary database on the same source, or the other source's configured default. All analyses remain required. Excel source sheets include source and database names, and the immutable snapshot records provenance for each analysis. Joins remain within a database; cross-database comparisons use separately captured analyses. The assistant must investigate overlapping replicas/archives before adding totals and keep currencies separate. Discovery can only reach servers configured as sources and databases allowed by their reporting logins.

Annual exports that exceeded the former 50 MB/100,000-row limits must be requested again after upgrading. A blocked report has no saved data snapshot, so raising capacity does not turn its existing card into a completed workbook. The new capacity preserves complete detail and supplementary breakdowns; it does not bypass Excel's worksheet limits, security isolation or validation. Large JSON encoding/decoding runs off the HTTP event loop, and gathered row copies are released before the isolated workbook worker starts. Worker execution remains bounded to five minutes and 4 GiB; compressed output files remain bounded, and validation accepts at most 2 GiB of uncompressed workbook XML.

## Managing several server connections

Use **Burimet e të dhënave → Shto lidhje** for each SQL Server host/login. The required display name identifies the connection, not a database. A connection with no default database checks the server catalog through master, and the model supplies an inventoried business-database name for subsequent discovery, queries and reports; business tools cannot silently query master. **Shiko databazat** shows a paginated list of accessible online business databases. SQL login permissions and source grants apply throughout.

**Shkëput** persistently disables a connection without erasing its private `.env` profile; **Rilidh** enables and checks it again. Disconnected sources disappear from model discovery, cannot be used by legacy datasets, and results from an in-flight query are withheld if the connection was disconnected before it returned. Queries use short-lived connections, closed/rolled back after each read. **Hiq lidhjen** removes the application connection, encrypted credentials and source grants; linked legacy datasets are detached and disabled. Existing report snapshots and Excel files remain. Server databases and external `.env` files are never deleted. Environment-profile bindings persist independently of source ordering, so deleting one connection does not silently bind another to its credentials.

In connection configuration, **Zbulo automatikisht të gjitha databazat** clears an existing saved default database while preserving the other saved credentials. Blank credential fields on edit keep their current values; selecting a default database is optional. For updates, omitted, empty, or null connection fields preserve their existing values for both SQL Server and SAP HANA, including environment-backed profiles. API clients may PATCH a single field without resending metadata or credentials. Use `discover_databases: true` (the automatic-discovery checkbox) to explicitly clear the default database. New connections still require complete credentials.

## SAP HANA connections

Choose **SAP HANA** in **Burimet e të dhënave → Shto lidhje**. An existing SQL Server connection can also be edited to SAP HANA; specify its actual HANA SQL port when changing engine. The backend uses SAP's `hdbcli` driver, double-quoted identifiers and bound HANA parameters; SQL Server query scripts are not sent to HANA. Configure `HANA_HOST`, `HANA_PORT`, `HANA_USER`, `HANA_PASSWORD`, and optionally `HANA_DATABASE`. On-premise ports depend on the installation (30015 is an example, not a universal default); HANA Cloud uses its supplied endpoint, usually 443 with TLS. TLS and certificate validation default to enabled. Use the server's trusted certificate chain; change TLS options only to match the actual server configuration.

An empty database name discovers accessible tenants where the endpoint and login permit it. A tenant-only login still discovers all visible business schemas in its connected tenant, with an explicit catalog warning. SAP Business One companies are usually schemas within a tenant; do not put a company schema into `HANA_DATABASE`. SYSTEMDB is used only for catalog/routing, never business reports. Additional tenants may need their own SQL endpoint/connection and grants. All saved fields, including TLS settings, are written to the project `.env` under the connection's displayed prefix. Saving takes effect immediately; replacing the host file with an editor requires the permission script and container recreation once.

[Official SAP Python connection guide](https://help.sap.com/docs/PRODUCT_ID/f1b440ded6144a54ada97ff95dac7adf/d12c86af7cb442d1b9f8520e2aba7758.html)

Workbook validation decodes OOXML shared-string escapes before comparing every protected source cell. Carriage returns and literal escape sequences remain distinct. Failed script attempts retain the candidate document and a safe validation diagnostic in the audit/Excel traffic events; a downloadable workbook is published only after full validation.

All business calculations now use the general model-authored workflow below. The fixed `calculate_balances` and `create_balance_report` tools are retired: old chat calls return a migration explanation without querying, calculating or creating a report. Direct API requests with `balance_reconciliation` are rejected. Historical report snapshots and downloaded workbooks remain readable; their integrity/rendering support is retained only for saved artifacts.

All report types use a shared public-snapshot boundary that keeps `_internal` audit data out of model context and public exports. The model chooses the exact output datasets; asking for more detail does not authorize additional periods, clients or reconciliation.

## Model-authored data calculations

ChatGPT and Claude share `calculate_data` and `create_calculation_report`, the same authenticated handler, and the same calculation/export validation. The model discovers database metadata and evidence, determines the business rules, and authors `calculate(tables)`. The backend retrieves complete structured query results and/or complete uploaded tables, then executes that script in a private Linux worker with AST restrictions, Landlock, seccomp, memory/CPU limits and cancellation. There is no direct SQL, credential, filesystem, shell, network or provider-specific execution fallback. Failure of isolation or any requested input fails the entire calculation. Query preview limits never limit calculation input; cumulative configured row/byte limits fail without partial results.

Scripts support conditional signs, grouping, dictionary joins on full business keys, eligibility logic and comparisons with uploaded references. `number()` uses Decimal, `date_of()` handles ISO/SAP dates, `require()` aborts failed integrity checks and `divide()` makes rounding explicit. Ordinary arithmetic traps inexact results. The model must investigate invoice versus payment rules, account classifications, duplicate joins, currencies and conflicting reference evidence. There is no fixed accounting calculator or backend-selected balance formula. This execution path is independent of company names, schemas and database engines; the configured connectors currently support SQL Server and SAP HANA. Successful execution does not certify the chosen accounting interpretation. No dates, SAP clients, account lists, partner thresholds or reference-specific rules are hardcoded.

Each successful run captures the inputs, query plans, script, chosen rules, counts, hashes and typed outputs in owner/conversation-scoped `calculation_runs`. Multiple input queries are independently captured, not an atomic snapshot across databases. Chat receives the model script's typed output datasets with explicitly bounded previews and row counts. The model must return its own small summary/control datasets when totals are needed; the backend never sums arbitrary output columns, identifiers, ratios or financial measures. Calculation alone creates no report or Excel. When requested, `create_calculation_report` selects named output datasets from that exact run, without re-querying live data or changing formulas. Source grants are rechecked before capture and export. Excluded raw inputs remain private audit evidence, retained in the report snapshot across chat deletion and stripped by the shared public-snapshot boundary. Export only the requested outputs; later adjustments/revised balances still require explicit reconciliation.

Calculation exports store selected output rows once, in the report's primary/additional datasets. Private audit evidence retains the complete original query inputs, model code and per-output row counts/hashes rather than a duplicate copy of all calculated rows. Older snapshots are compacted before size checks only after verifying that every selected row and column schema matches its existing report copy. This does not rerun queries or calculations, truncate data, or raise resource limits.

Older saved Codex catalogs can use `create_database_report` with `instructions` containing `CALCULATE_DATA`, a newline, and the JSON calculation plan; this is a read-only compatibility mode. `EXPORT_CALCULATION` plus newline/JSON containing `calculation_id` and `calculation_datasets` exports the captured result. These envelopes bypass report creation or wrapper queries as appropriate, preserving native conversation IDs. New catalogs and Claude use the dedicated tools directly.

Model investigations have no application-imposed wall-clock deadline by default (`TURN_TIMEOUT_SECONDS=0`) for either ChatGPT or Claude, in chat and background report inference. The existing frontend stream remains open until a terminal result; no automatic user follow-up, new conversation, or duplicate request is needed after five minutes. Both providers send a keepalive every 15 seconds while quiet, including during long tool calls; a keepalive never cancels the underlying work. Stop and client disconnect still interrupt/cancel the response and release its worker. Actual provider/connection failures remain explicit; work is not blindly restarted after ambiguous network failures. A positive `TURN_TIMEOUT_SECONDS` opts into a response deadline; negative values are rejected. Login/transport handshakes, database queries and isolated calculation/workbook workers retain their separate operational limits; they are not five-minute model-investigation deadlines.

### Recovery, chat versions and account access

Accepted chat turns run independently of the browser connection. SQLite checkpoints each streamed reply event and message text; a refresh reopens the selected chat and follows its saved progress. Reconnection uses an owner-scoped request key and event cursor, so retrying a lost transport does not submit the same message twice. On application startup, unfinished turns restart automatically in a new native thread with the complete earlier transcript, the original request, the unverified partial draft and existing report references. Both ChatGPT and Claude use this path. The provider may repeat unfinished investigation steps; recovery does not claim to restore its private reasoning or SDK execution state. Stop, password recovery and account deactivation cancel accepted work instead of automatically resuming it.

Queued/running reports retain their generation recipe and captured snapshot. Restart resumes that report ID, consumes additional analyses once, and reuses a completed narrative/workbook script when available. Snapshot permission receipts are revalidated before model processing and publication. Legacy unfinished reports without a persisted recipe remain failed rather than being reconstructed from an unknown scope. Provider authentication/usage errors remain visible failures requiring the relevant account connection or retry.

Rebuilding native model context sends the complete completed transcript, without the previous 40-message cutoff. Report generation also receives the chat history so earlier exclusions remain available. Editing or restoring a chat invalidates both native provider bindings. **Versionet e bisedës** restores an archived transcript and its attachment links while retaining the displaced version; completed reports keep their files and snapshots.

Browser-local drafts retain text, attachment selections, edit targets and model/effort choices per member, including a not-yet-created chat. Draft persistence is best effort when browser storage is unavailable. Add-member/dataset/source forms reject repeated submissions while saving.

Members change passwords in **Cilësimet** using their current password. Devs can issue a one-use, 30-minute recovery code from the member list; deliver it privately. The member uses **Harrova fjalëkalimin** on the sign-in page to set a new password. Issuing another code replaces the previous one. Successful changes/resets revoke old sessions and recovery codes and stop current work; no database, company or dataset grants are changed. Codes and passwords are excluded from traffic/audit payloads. The legacy source-wide grant endpoint preserves already-existing grants idempotently but rejects new broad grants; use the database/company picker for new assignments.

### Multiple subscriptions and automatic continuation

In **Cilësimet → Modeli**, Devs can add and connect multiple shared ChatGPT or Claude subscriptions, enable/disable them, and arrange each provider's fallback order with the arrow buttons. Each account has its own native credential directory. Existing connections are adopted in place; migration does not copy tokens, change members, or rewrite database/company grants. Subscription tokens and authorization codes are never placed in conversation checkpoints.

On a terminal subscription quota/authentication failure, a chat or background report tries the next enabled, connected account of the same provider, then the other provider. Each account is attempted at most once per request. A cross-provider move to Claude requires **Claude Opus 5.5** (`claude-opus-5-5`) in that account's actual model catalog; an unavailable model is never invented or silently replaced with Sonnet. A move to ChatGPT uses its catalog default. Explicit reasoning effort is retained when supported, otherwise mapped to an equal or stronger supported effort, or the highest available level. The effective model/effort are saved with the chat.

Before switching, the backend checkpoints the local transcript, successful and failed tool evidence, calculation plans/captured-result references, existing reports, and the unfinished draft (marked unverified). Large contexts are compacted on the destination subscription; exact, hashed evidence remains available through owner- and conversation-scoped `read_handoff_context` pages. Private internal thinking is not transferred. Credential changes invalidate only that account's native bindings, while local history remains. Discarded chat branches cannot supply active handoff evidence. Current grants and capture receipts are revalidated before evidence is transferred or reread.

Provider-supplied reset times are respected. If a provider omits its reset time, a new request may probe the account once; status polling does not start inference or repeatedly retry it. Devs can also use **Provo përsëri** after checking an account. There is no fixed model investigation time limit unless `TURN_TIMEOUT_SECONDS` is explicitly configured. Cancellation still stops the current continuation. When all accounts are unavailable/exhausted, or context cannot be validated, the response ends with a saved, readable error and releases the chat for the next request. Generic transport, database and permission failures are not disguised as subscription exhaustion.
